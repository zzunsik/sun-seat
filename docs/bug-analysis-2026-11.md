# 화면·지도 버그 근본 원인 분석과 구조 개선 설계 (#167)

2026-11-19~21 사이 화면·지도 버그가 연달아 나왔다. 이 문서는 버그마다 실제 원인 코드와 "왜 테스트·리뷰·실기기 확인이 못 잡았는지"를 정리하고(#167 1차 가설 확인·반박), 묶음별 근본 원인에 대한 구조 개선 설계와 구현 이슈 순서를 정한다.

- 기준: `origin/develop` `06fcf13`(PR #166, #162 머지 뒤). 버그 표의 코드 위치는 `29b780f` 기준으로 읽었다. 진행 중: 초안 PR #165(#155), 브랜치 `fix/141-list-map-fit`(#141, 일부 구현).
- 근거는 각 이슈 본문, 고친 PR의 "원인·재현·실기기" 절, 현재 코드다. 코드 위치는 `app/src/main/java/com/sunseat/app/` 아래 상대 경로다.
- 제품 코드는 바꾸지 않는다(`조사`). 구현은 7장의 이슈에서 한다.

## 1. 요약

1. **지도 카메라 결정이 한 곳에 없다.** 맞춤 대상·시점·여백이 `CandidatesScreen`(`fitTrigger`·`userMoved`·`fitEnabled`), `MapFitPolicy`(`requested`·`labelMargins`), `fitFrame`(inset·표식·이름표 여백), `NativeMap`(`setPadding`+`fitMapPoints`, 따라가기 `newCenterPosition`)에 흩어져 있고, 버그 하나를 고칠 때마다 인자 하나가 늘었다(#138 → #143 → #151 → #153). 가설 **확인**.
2. **테스트 지도가 네이티브 지도와 다르게 움직이는 곳에서 버그가 났다.** 테스트 렌더러(`MapPlaceholder`)는 연속 배율로 투영하고, 여백이 바뀌어도 카메라를 옮기지 않으며, 매 프레임 표식을 다시 배치한다. 카카오 지도는 정수 줌이고, `setPadding` 때 화면 내용이 움직이고(#148, 실기기 관찰), 표식 재배치는 `update()`와 카메라 이동 끝에서만 한다(#153). #148은 Robolectric이 원리상 재현할 수 없었고, #138은 정수 줌 효과가 테스트 지도에서 작게 보였으며(순수 함수 `MapFitFrameTest`로는 재현됨), #153은 첫 수정이 테스트 지도에서만 통과했다.
3. **후보 화면은 상태 하나가 아니라 이벤트별 효과의 합이다.** 시트 높이·미리보기·선택·스크롤·초점·방향이 `remember` 변수 10여 개와 `LaunchedEffect` 여러 개로 나뉘어, 이벤트 하나(범주 변경, 미리보기 닫기, 끌기)에 필요한 효과를 각자 붙였다. 빠진 효과가 버그가 됐다(#136 #145 #158). 가설 **확인**.
4. **여백은 측정값이 아니라 어림값으로 시작했다.** 고정 dp(`Sizes.simulationMapInfo` 84dp, 시트 내용 720dp)와 측정 순서에 따라 바뀌는 값(축약 여정 바 높이)이 원인이었다(#101 #161 #162). #113은 고정 높이 장면이 줄바꿈되는 글 아래에 있어 밀린 배치 문제였고, 시스템 바 없는 테스트 설정이 이를 가렸다. 가설은 **부분 확인**: #134·#155는 겹침이 아니라 정렬·스크롤 경계 표시 규칙이 없던 문제다.
5. **표식 겹침은 "숨김"과 "비키기"가 따로 생겼고 정보 우선순위가 없었다.** 차량에 가린 글자 숨김(#146)이 꼭 남아야 할 정보까지 숨겼고(#152), 출발 핀–이름표(#153)와 출발 핀–도착 핀(#160)은 각각 따로 규칙이 필요했다. 가설 **확인**, 그리고 "정보 우선순위" 개념이 추가로 필요하다.
6. **검증은 정지 화면 위주였다.** 전환(미리보기 닫기, 끌고 나서 누르기, 회전)·시스템 바 인셋·큰 글자 조합을 거의 보지 않았고, 실기기 확인도 정상 경로 한 상태가 대부분이었다. 11-20 develop 빌드 일괄 실기기 점검 한 번에 8건(#134 #135 #136 #143 #144 #145 #146 #147)이 나왔다(여러 PR에서 온 것이고 일부는 그 전부터 있던 동작이다).
7. **고친 PR이 다음 버그를 만들었다.** #142(#138)가 inset을 줄여 #151, #149(#146)가 표식을 숨겨 #152, #111(#101)의 축약 여정 바 측정이 #162로 이어졌다. 규칙이 한 곳에 없어 수정의 영향 범위를 테스트가 보지 못했다.

묶음: **카** 지도 카메라·맞춤, **상** 후보 화면 상태·제스처, **오** 오버레이·여백·레이아웃 불변식, **표** 표식 겹침, **가** 지도 사용 가능 상태.

## 4. 구조 설계

### 4.1 지도 카메라 정책 단일화 (구현 #168)

**근본 원인.** 카메라가 언제·어디로·얼마나 움직일지가 화면 코드와 지도 코드에 나뉘어 있고, 그 결정의 일부(여백)를 SDK의 `setPadding`에 맡긴다. 여백은 매 프레임 바뀌고(시트), SDK는 여백 변경을 카메라 이동으로 처리하며, 테스트 지도는 그렇지 않다. 맞춤은 좌표만 알고 표식·이름표가 화면에서 차지하는 크기는 인자로 하나씩 덧붙였다.

**설계.**

```
카메라 모드: Fitted(대상) | UserMoved | Following(차량) | Centered(지도 선택)
요청: Fit(이유) · Gesture · FollowStart · FollowStop · ViewportChanged · GeometryChanged

cameraPolicy(mode, request, input) -> CameraDecision
  input = 보이는 영역(px 사각형: 지도 크기 − 측정한 오버레이),
          표식 발자국 목록(좌표 + 좌표 기준 화면 상자: 핀·이름표·차량),
          줌 → 배율 함수, 최소 틈
  CameraDecision = None | MoveTo(center: LatLng, zoom: Int) (+ 다음 모드)
```

- **보이는 영역이 바뀌어도 카메라를 옮기지 않는다.** `Fitted`·`UserMoved`에서 `ViewportChanged`(시트 끌기, 오버레이 높이 변화)는 `None`이다. `Following`에서는 차량을 새 보이는 영역 가운데로 다시 둔다(줌 유지). 네이티브 지도에 `setPadding`을 쓰지 않거나 0으로 고정하고, 맞춤 결과는 `newCenterPosition(center, zoom)`으로 적용한다. 보이는 영역이 지도 가운데가 아니므로 정책이 그 중심 차이만큼 카메라 중심을 옮겨 계산한다(그 위도의 m/px 필요). 그러면 시트를 움직여도 화면 내용이 그대로다(#148). #71 계약(시트 이동만으로 다시 맞추지 않음)과 같다.
- **카카오 로고**: 여백을 0으로 두면 SDK가 로고를 지도 전체 기준으로 두어 시트 밑에 들어갈 수 있다. 로고 위치(`Logo.setPosition` 등)도 정책의 보이는 영역에서 정한다(DESIGN 11: 로고는 가리지 않는다).
- **맞춤은 표식 발자국 전체를 넣는 가장 큰 정수 줌**을 찾는다(지금처럼 최대 줌 17 제한 유지). 핀 높이(#138), 이름표 폭(#143), 이름표 높이(#151), 출발 핀을 비킨 이름표(#153)를 인자별 여백이 아니라 발자국 하나로 다룬다. 줌이 정수라는 사실을 정책이 알므로 #138 같은 "두 단계 멀어짐"을 계산에서 바로 본다.
- **모드가 상태다.** "지도 맞춤" 행동은 `UserMoved`일 때 보인다(#141). 따라가기 중에는 이름표 여백을 쓰지 않는다는 #146·#143의 분기(`labelMargins`)가 모드에서 나온다. 미리보기 닫기(#135)·선택 변경·가로 전환(#144)은 `Fit` 요청이고, 실행 여부는 모드가 정한다.
- **두 렌더러가 같은 결정을 적용만 한다.** 테스트 지도도 정수 줌·같은 중심으로 투영해, 줌 단계 차이가 Robolectric에 그대로 보인다. 렌더러 차이(R)가 줄어든다.
- 줌 → 배율: 테스트 지도는 Web Mercator(2^z) 해석식, 네이티브는 첫 단계에서 실기기로 잰 값(또는 `fromScreenPoint`로 런타임 측정)을 넣는다. **구현 첫 단계에서 실기기로 `setPadding` 전후 카메라 위치와 줌별 m/px를 기록해 #148의 SDK 동작 가설을 확인한다.** 가설이 틀려도(예: 여백 변경이 카메라를 옮기지 않음) "정책이 중심·줌을 직접 정한다"는 설계는 그대로 쓸 수 있다.
- **성질 기반 테스트**(외부 라이브러리 없이 고정 시드 `Random` 반복): 임의 경로(정류장 1~30개, 남북·동서·대각·되돌아오는 경로), 보이는 영역(320×110dp 띠 ~ 844×390dp), 글자 1.0/1.5배 이름표 폭, 위·아래 오버레이에서
  - 모든 발자국 상자가 보이는 영역 안(최소 틈 포함)
  - 한 단계 더 가까운 줌에서는 어느 발자국이 밖으로 나간다(최대 줌, 줌 17 상한에 걸린 경우 제외)
  - `Fitted`·`UserMoved`에서 `ViewportChanged`만으로는 `None`, `Following`에서는 차량이 새 보이는 영역 가운데
  - 모드 전이표(사용자 이동 뒤 선택 변경 = 맞춤, 사용자 이동 뒤 정렬 = 없음 등, DESIGN 12.3)
- 기존 테스트(`MapFitFrameTest`, `MapLabelMarginTest`, `MapLabelEdgeTest`, `FollowCameraTest`, `PreviewCloseRefitTest`, `MapPickProjectionTest`)는 지우지 않는다. 얇은 어댑터를 남겨 그대로 돌게 하는 것을 기본으로 한다. test-guard는 테스트를 옮기기만 해도 실패하므로, 옮기거나 기대값을 바꾸면 값이 같아도 PR에 `테스트 기대값 변경: <사유>`를 적는다. 테스트 지도를 정수 줌으로 투영하면 지도가 있는 기준 이미지 대부분이 바뀌므로 CI 기록과 바뀐 이미지 확인을 같은 PR에서 한다.
- #141 브랜치(`fix/141-list-map-fit`: 목록 지도 띠의 "지도 맞춤" 행동, `ListMapFitActionTest`, 기준 이미지 2장)는 화면 쪽 구현으로 재사용하고, 보이는 조건만 `userMoved` 대신 `UserMoved` 모드로 바꾼다.

### 4.2 후보 화면 상태 모델 (구현 #171)

**근본 원인.** `CandidatesScreen`은 `showPreview`, `sheetBeforePreview`, `restorePending`, `restoringExpanded`, `revealSelected`, `previewShown`, `fitTrigger`, `fittedTrigger`, `userMoved`, 측정 높이 10개(`headerHeight`~`fitActionBottom`)를 따로 들고, 전환마다 `LaunchedEffect`가 순서에 기대어 효과를 낸다. 이벤트 하나에 필요한 효과를 빠뜨리거나(#136 #145 #158) 측정 순서가 시트 앵커를 바꿨다(#162).

**설계.**

```
CandidatesUiState(
  sheet: Default | Expanded,           // 가로(#144)는 시트 없음
  preview: null | Preview(id, sheetBefore, scrollAnchor),
  selectedId, category, sort,
  scrollAnchor: Top | Item(id, offset),
  camera: (4.1의 모드),
  gesture: Idle | DraggingSheet,
  orientation: Portrait | Landscape,
)
reduce(state, event) -> (state, effects)
  event: CardTap · PreviewClose(Back|버튼) · SeatOpen · ReturnFromResult · SheetSettled(anchor)
         · DragStart · DragEnd · CategoryChange · SortChange · Rotate · FitAction · MapGesture · JourneyBarTap
  effect: AnimateSheet(anchor) · ScrollTo(Top|Item) · FocusCard(id) · Camera(요청, 4.1)
```

- 순수 함수라 JVM 단위 테스트로 **전환표 전체**를 돈다(상태 × 이벤트). 범주·정렬 변경 = `ScrollTo(Top)`(#136 #83), 미리보기 닫기 = `AnimateSheet(sheetBefore)` + 선택 카드가 안 보이면 `ScrollTo(Item)` + `FocusCard(id)` + `Camera(Fit)`(#145 #158 #135), 회전 = 같은 상태를 다른 배치로(#144).
- **시트 앵커는 끄는 동안 바뀌지 않는 값으로 정한다.** 최대 높이·peek는 화면 크기·글자 크기·인셋에서 나오고, 끄는 도중 처음 측정되는 부품 높이에 기대지 않는다(#162의 원인을 규칙으로). `DraggingSheet` 동안의 측정 변화는 다음 `Idle`에서 반영한다. PR #166(`06fcf13`)은 끄는·정착하는 동안 축약 여정 바의 이전 높이를 유지하고 정착 뒤 새 측정을 반영하는 방식으로 이 규칙을 먼저 적용했다. #171은 이를 상태 모델의 일반 규칙으로 옮긴다.
- Compose 층은 상태를 그리고 이벤트만 보낸다. 상태는 `rememberSaveable` 하나로 저장한다(회전·재생성).
- **전환 테스트 패턴**(Robolectric, `FlowTestGraph`): 실제 터치(`performTouchInput { swipeUp() }` → 정착 대기 → `click()`), 미리보기 열기/닫기(기본·완전 확장 각각), 회전(`RuntimeEnvironment.setQualifiers` 뒤 재생성), 범주·정렬, 결과에서 돌아오기. 각 전환 뒤에 시트 값·선택·스크롤·초점·카메라 요청을 함께 단언한다.
- PR #166(#162)의 `SheetDragTapTest`는 그대로 남겨 회귀를 막는다.

### 4.3 오버레이·여백 공통 틀 (구현 #172)

**근본 원인.** 지도·본문 위에 겹치는 부품(헤더, 정보 카드, 조작 패널, 떠 있는 행동, 따라가기 줄)의 높이를 화면마다 다르게(고정 dp, 어림값, 측정값) 다루고, 본문 글자가 그 밑에 깔리는지 공통으로 검사하지 않았다. 스크롤 영역의 경계 표시 규칙도 없었다.

**설계.**

- **측정 오버레이 등록**: 겹치는 부품은 `Modifier.overlayOf(영역)`(가칭)로 자기 화면 상자를 등록하고, 지도는 등록된 상자로 4.1의 "보이는 영역"을, 스크롤 본문은 `contentPadding`을 받는다. 고정값(`Sizes.simulationMapInfo` 84dp 등)은 측정 전 첫 프레임 어림으로만 쓰고 측정 뒤에는 쓰지 않는다(#161, #103의 방식을 공통화). 가로 3D 장면처럼 고정 높이 부품은 줄바꿈되는 글보다 위에 두거나 가용 높이로 제한한다(#113).
- **공통 검사** `assertNoTextUnderOverlays()`(테스트 도우미): 의미 트리의 글자 노드마다 화면 상자가 같은 화면의 오버레이 상자와 겹치지 않는지, 스크롤 영역 밖으로 잘리면 경계 표시가 있는지 확인한다. 지도 표식은 테스트 지도가 그린 발자국 상자(4.1)로 같은 검사를 한다. 모든 화면 스크린샷 테스트가 세로 390dp, 320dp·1.5배, 가로 832×384dp + 시스템 바 인셋에서 이 검사를 함께 돈다.
- **스크롤 경계 표시 규칙**을 DESIGN 4장에 정한다. 초안 PR #165의 흐림 띠는 리뷰에서 DESIGN 8장의 장식용 그라데이션 금지와 충돌한다는 지적을 받았고 리뷰에서 글자 윗부분이 여전히 보이는 문제가 나왔으므로, 구분선 등 금지 규칙과 맞는 방식으로 정한다. #165의 `SimulationDetailsEdgeTest`는 재사용하고 #165는 이 이슈의 PR로 대체한다.
- 큰 글자에서 단어 중간 줄바꿈(#161 "재생", "표준 시내버스(추정)")은 DESIGN 4.4(큰 글자·작은 화면 예외)에 버튼·라벨 규칙으로 넣는다.
- 목록 항목 좌우 여백(#134)처럼 "같은 열은 같은 시작 x"도 이 도우미에 넣는다.

### 4.4 표식 배치 규칙 (구현 #170)

**근본 원인.** 겹침 처리가 `NativeMap`의 그리기 순위(`PLACE_RANK` > `STOP_RANK` > `STOP_NAME_RANK`), `coveredByVehicle`(숨김, #146), `visibleCursor`(도착 시 차량 거둠, #152), `stopLabelOffset`(비키기, #153)에 흩어져 있고, 무엇을 숨겨도 되는지 기준(정보 우선순위)이 없다. 네이티브는 `update()`와 카메라 이동 끝에만 다시 배치하고 테스트 지도는 매번 다시 그린다.

**설계.**

```
markerLayout(marks, projection) -> placements
  mark = (종류, 좌표, 상자 크기, 우선순위, 대체 정보 위치)
  placement = 기본 자리 | 비킨 자리(dx, dy) | 숨김(대체 정보가 있을 때만)
```

- **우선순위 표**를 DESIGN 11.1에 둔다(초안): 도착 핀(도착 뒤) ≥ 출발·도착 핀 > 차량(재생 중) > 승차·환승 노선 이름표 > 정류장 원 > 진행 화살표.
- **처리 순서**: 겹치면 낮은 쪽을 정해진 방향으로 비킨다(이름표: 핀 바깥, 핀–핀(#160): 한쪽을 옆으로) → 비킬 자리가 없으면 숨기되, **그 정보가 다른 곳(정보 카드, TalkBack 요약)에 있을 때만** 숨긴다(#152). 숨김에는 대체 위치를 단언하는 테스트를 붙인다.
- 같은 함수를 테스트 지도(그릴 때)와 네이티브(카메라 이동 끝·줌 변경·숨김 변화 때)가 부른다. 4.1 맞춤은 이 배치 결과의 발자국을 쓴다(비킨 이름표 포함). 비킴은 화면 거리라 줌에 따라 달라지므로, 맞춤은 후보 정수 줌마다 그 줌의 투영으로 배치를 계산해 발자국을 얻는다(줌 단계는 많아야 수십 개라 비용이 작다).
- 성질 테스트: 임의 좌표 쌍·이름표 폭에서 보이는 표식끼리 상자가 겹치지 않음, 숨김은 대체 정보가 있는 것만.

### 4.5 지도 사용 가능 상태 (구현 #173)

- 지도 상태에 `Availability`(준비 중·사용 가능·사용 불가(키 없음/인증 실패))를 두고, 렌더러 경계(`LocalMapRenderer` 또는 별도 제공자)에서 바꿀 수 있게 한다. 지금도 `NativeMap`은 `keyAvailable` 인자를 받고 사용 불가 스크린샷 테스트가 있지만, 화면 테스트는 테스트 렌더러로 그려 실제 안내 노드가 화면 의미 트리에 나타나지 않는다. 테스트 렌더러도 사용 불가 상태에서 네이티브와 같은 안내 노드를 그리게 한다.
- 지도 화면마다 사용 불가 상태의 접근성 트리를 단언한다(안내 한 번, 경로 지도 설명 없음).
- 사용 불가일 때 지도 노드는 안내를 한 번 읽고(경로 지도 설명·경로 요약을 읽지 않음), 화면 아래 안내와 중복 낭독하지 않도록 낭독 출처를 하나로 정한다. 지도 선택·후보·결과·시뮬레이션이 같은 규칙을 쓴다(#147).

## 5. 테스트·프로세스 보강

### 5.1 테스트 패턴

- **결과를 단언한다**: 맞춤 횟수·revision 대신 "발자국 상자 ⊂ 보이는 영역", "글자 ⊄ 오버레이", "보이는 표식끼리 비겹침". revision 단언은 보조로만 쓴다.
- **제스처 뒤 누름은 실제 터치로**: 끌기 → 정착 대기 → 누르기를 `performTouchInput`(또는 실제 터치를 보내는 `performClick()`)으로 한다. 의미 동작(`performSemanticsAction`)은 제스처 상태를 건너뛰므로 접근성 동작 자체를 검사할 때만 쓴다.
- **전환 테스트**: 4.2의 전환표. 한 테스트가 한 전환을 보고, 전환 뒤 상태 전체(시트·선택·스크롤·초점·카메라 요청)를 단언한다.
- **환경 행렬**: 세로 390dp, 320dp·1.5배, 가로 832×384dp + 시스템 바 인셋 24dp(#113 PR #126이 처음 쓴 설정)를 화면 불변식 검사의 기본 행렬로 쓴다.
- **렌더러 차이 목록**: 테스트 지도가 재현하지 못하는 것(카카오 로고, SDK 제스처 관성, 실제 타일·GPU)을 이 문서에 두고, 그 영역을 바꾸는 PR은 실기기 점검을 필수로 한다. 4.1·4.4 뒤로는 정수 줌·여백 비의존·재배치 시점 차이가 목록에서 빠진다.

### 5.2 실기기 기본 점검 스크립트 (구현 #169)

`scripts/device-smoke.sh`(bash, adb + `uiautomator dump`)와 사용법 문서. 실기기가 기본이고, Android 에뮬레이터는 선택적 교차 확인(`-s <serial>`)이다.

- 준비: debug 빌드에 `testTagsAsResourceId`를 켜 테스트 태그로 노드를 찾는다. 글자 크기(`settings put system font_scale`)·회전(`settings put system user_rotation`)을 스크립트가 바꾸고 끝나면 되돌린다.
- 흐름(공개 POI 서울역 → 강남역만 쓴다):
  1. 목록 첫 진입: 헤더 아래끝 ≤ 시트 손잡이 위끝, 지도 띠 높이 > 0
  2. 손잡이로 끌어 완전 확장 → 카드 누름 → 미리보기 열림(#162)
  3. 시트를 약 60dp 올렸다 내림 → 지도 발자국 로그가 전과 같음(#148)
  4. 완전 확장에서 미리보기 열기 → 닫기 → 시트 완전 확장, 선택 카드 보임, 맞춤 1회(#135 #145)
  5. 목록·미리보기에서 회전 → 카드 1장 이상 보임, 지도 맞춤(#144)
  6. 글자 1.5배 시뮬레이션: 정보 카드·조작 패널과 글자·지도 발자국 비겹침(#113 #155 #161)
  7. 따라가기 끄기 → 따라가기 줄이 지도와 겹치지 않음(#122)
  8. 지도에서 위치 선택 열기·선택
- 지도 안 표식은 접근성 트리에 없으므로, debug 빌드에서만 4.1 정책이 보이는 영역과 발자국 상자(px, 좌표 없음)를 logcat 한 줄로 남기고 스크립트가 읽는다(#168에서 추가). 그 전에는 Compose 쪽 검사만 한다.
- 화면 캡처는 로컬 결과 폴더에만 두고 커밋하지 않는다(AGENTS.md "데이터와 개인 정보").

### 5.3 머지 전 실기기 확인 범위

- 지도 카메라·표식·시트·제스처·회전·시스템 바에 닿는 PR은 auto-merge 전에 5.2 스크립트의 해당 흐름을 실기기에서 돌리고 결과를 PR에 적는다. "후속 일괄 검증"으로 미루고 머지하지 않는다.
- 그 밖의 화면 PR은 스크립트 전체 흐름 통과(또는 "실기기 미검증"과 사유)를 적는다.
- 위 규칙은 AGENTS.md "PR"·"테스트"·"화면 작업" 절과 "겪고 나서 추가하는 규칙"에 근거와 함께 넣고, PR 템플릿 확인 목록에도 반영했다(이 PR).
